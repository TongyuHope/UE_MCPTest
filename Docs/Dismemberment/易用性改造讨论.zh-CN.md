## 1. 核心判断：现在的抽象层次放错了

现有 API 的心智模型是"**对某骨骼执行摘除 + 施加冲量**"：

```cpp
bool ApplyDismemberment(const FName& BoneName, const FDismembermentConfig& DismembermentConfig);
```

而动作组脑子里想的是"**这段动画播到这里，这个部位断掉，往这个方向飞出去，差不多这么大劲儿**"。

两者之间隔了三道需要专业知识的鸿沟：

1. **骨骼名**：要从骨架里找出准确的名字并手工敲进去，敲错就静默失败。
2. **坐标系**：`WorldSpace` / `BoneSpace` 是坐标变换概念。而 `BoneSpace` 的语义还特别反直觉——它取的是"**断口骨骼的朝向**"，不是角色朝向。动作组想表达"往角色右后方飞"时，几乎不可能靠心算得出正确的局部向量。
3. **物理参数**：`ImpactForce`（速度增量）、`AngularImpulseDegrees`（度）、`bVelChange` 全部是物理量，没有视觉参照就无法调。

**改造主线：把抽象层次上移到动作组的意图层，把这三道鸿沟各自封进引擎侧。** 后文所有建议都服务于这条主线。

## 3. P0：先解决"看不见"和"重复劳动"

### 3.1 断肢失败必须说话（建议 1）

**问题**：`UDismembermentComponent::ApplyDismemberment()` 有约 10 处 `return false`，**全部没有任何日志**。动作组遇到的最典型场景是"我按了，但什么都没发生"，而此时唯一的线索是编辑器 Output Log 里也什么都没有。

**现状的失败点**（对应 `DismembermentComponent.cpp` 行号）：

| 行 | 失败原因 | 动作组能否自行理解 |
| --- | --- | --- |
| :34 | Owner/World 无效 | 否（引擎问题） |
| :35 | 驱动网格未解析 且 未指定目标网格 | **否，但这是最常见原因** |
| :55 | 指定的目标网格名在角色上找不到 | 是（拼写问题） |
| :57 | 整网格模式却未指定目标名 / 指定成了主体网格 | 否（规则隐蔽） |
| :63 | 目标网格没有骨骼网格资产 | 是 |
| :68 | 数据资产为空 | 是 |
| :73 | 骨骼不在目标骨架上 | **是，但需要告诉他骨架里有什么** |
| :79 | 该骨骼未登记在配置里 | **是，同样需要提示** |
| :88 / :93 | 候选模型数组为空或填错了数组 | 是（提示该填哪个数组） |

**建议**：

1. 新增日志分类 `DECLARE_LOG_CATEGORY_EXTERN(LogDismemberment, Log, All)`，替换现有 5 处 `LogTemp` 的 `"LimbMesh is not valid!"`。
2. 每个失败点输出**可操作的**信息，而不是"失败"。例如：

```
LogDismemberment: Warning: 断肢失败 — 骨骼 'hand_r' 未登记在 DA_Dismemberment 的 DismembermentConfigs 中。
                    当前已登记的骨骼：hand_l, lowerarm_r, lowerarm_l
```

3. 骨骼名不存在时，**列出骨架中名字最接近的几个骨骼**（简单的编辑距离排序即可）：

```
LogDismemberment: Warning: 骨骼 'hand_rr' 不存在于骨架 SK_Mannequin 中。
                    是否想用 'hand_r'？
```

4. 加一个 `UFUNCTION(Exec)` 或蓝图函数做**全量自检**，一键报出"配置里每个骨骼是否存在、资源是否齐、数组是否填错"：

```cpp
UFUNCTION(BlueprintCallable, Category="Dismemberment|Debug")
void DumpDismembermentDiagnostics() const;
```

这一条改动量最小、收益最大，建议第一个做。

### 3.2 批量触发与默认配置集中化（建议 2）

**问题**：现在有两种落后于实际需求的设计：

- `ApplyDismemberment` 的蓝图/C++ 入口每次处理一条配置，尚无返回成功数量的批量函数。
- 动画通知已经支持 `TMap<FName, FDismembermentConfig>`（一次多根），无需叠多个通知；但每条配置仍需分别填写参数，没有共享默认值，也没有失败汇总、顺序保证和重复断肢保护。

**建议**：提供不依赖动画资产的批量入口，并让默认值可共享。

```cpp
/** 一次断多根骨骼，共用一份冲击参数。 */
UFUNCTION(BlueprintCallable, Category="Dismemberment")
int32 DismemberBones(const TArray<FName>& BoneNames, const FDismembermentConfig& SharedConfig,
    bool bInHideWholeTargetMesh = false);
```

返回值改为"成功断掉的骨骼数量"，便于调用方判断。

同时把**每个部位的"个性参数"下沉到数据资产**，让动画通知只负责"什么时候断、往哪飞"：

```
数据资产（一次配置，全局生效）           动画通知（每次断肢才填）
├─ 骨骼名 → 候选模型                      ├─ 骨骼名（从已有配置里选）
├─ 碰撞预设                               ├─ 方向 + 力度
├─ 默认物理模拟时长  ← 建议新增            ├─ 角冲量
└─ 默认存活时间      ← 建议新增            └─ 可选覆盖
```

> 这一条与 [4.6 节](#46-把每条物理参数下沉到数据资产) 的参数分层是同一个方向，落地时可以一起做。

### 3.3 骨骼名下拉选择（建议 3）

**问题**：动画通知和数据资产的 `TMap` 键需要手填；`TargetSkeletalMeshComponentName` 则是组件对象名，不是骨骼名。当前没有骨骼名下拉或编辑器骨架一致性校验，但运行时骨骼模式会校验 `GetBoneIndex`，通知的编辑器校验也会检查配置非空。

**建议**：分级实现，从便宜的做起。

1. **最便宜**：在数据资产的编辑器校验（`IsDataValid`）里检查骨骼是否存在、候选数组是否与 `LimbMeshType` 匹配。编辑器会直接把资产标红报错，不用等到运行时。
2. **进阶**：给 `TMap` 的键加 `meta = (GetOptions="...")` 之类的选项提供器，从目标骨架提取骨骼列表做下拉。需要写一个 `UObject` 函数返回 `TArray<FName>` 或 `TArray<FString>`。
   - 难点：选项提供器需要知道目标骨架，而 `BoneName` 与 `Skeleton` 之间的关联在当前数据结构里是**跨资产**的（骨架在网格上，配置在数据资产上）。可行的折中是让数据资产**显式持有一个 `USkeleton*` 引用**，专门用于编辑器下拉与校验。
3. **更进一步**：在数据资产的编辑器面板里做一个骨骼树多选，勾选即生成条目。

我倾向先做 1，再做 2；3 的投入产出比要看你们的骨骼数量（如果只是手部/脚部少数几个部位，2 就足够了）。

### 3.4 专用工作流文档（建议 10）

`Docs/Dismemberment/` 现有的三份文档是**工程视角**的（代码结构、参数表、排查表），对动作组来说信息密度过高、缺少"照着做"的路径。

建议另出一份 `Docs/Dismemberment/动作组操作手册.zh-CN.md`，要求是：

- 全流程图（建资产 → 挂组件 → 配骨骼 → 动画通知 → 预览），不超过一屏；
- 每一步配编辑器截图，标注要点哪里；
- **只讲 3 个数字**（方向、力度、角冲量）怎么调，给一套参考值起步；
- 一页"出问题先看这里"的对照表；
- 明确写清"哪些字段不要动"，让动作组知道边界在哪。

## 4. P1：降低专业知识门槛

### 4.1 两套骨架的骨骼名问题（最容易被低估）

目录中两个 `_Skeleton` 资产的实际使用关系未确认，需要检查以下情况：

- **骨骼模式**要求 `BoneName` 在**目标骨架**上存在（`DismembermentComponent.cpp:73` 的 `GetBoneIndex(BoneName) == INDEX_NONE` 检查）。
- 模型外观缺少手不代表骨架删除了手部骨骼；应检查目标网格实际 RefSkeleton。
- 于是：如果断肢后把角色切到 `没手` 骨架的网格，再用同一个骨骼名去断，就会因为骨骼不存在而被拒绝。
- 两套宿主骨架共用配置时，应检查每个键是否都存在，不能仅因 Skeleton 资产不同就断言无法共用。掉落物 Skeleton 也不要求与宿主一致，因为当前没有从宿主复制姿势。

**需要你确认**：`没手` 骨架里到底保留了还是删除了手部骨骼？两套骨架的骨骼命名是否完全一致？

**建议方向**（视你的回答而定）：

- 若两套骨架骨骼名一致：写一个校验命令，一次性核对配置中所有骨骼在两套骨架上是否存在。
- 若不一致：`FSKMDismembermentConfig` 应该增加"适用骨架"的维度，或者干脆为每套骨架各建一份数据资产，并在文档里明确对应关系。
- 静态网格可以减少掉落物自身的骨架/Physics Asset 配置，但不会绕过宿主骨骼模式的骨骼名校验。当前 SkeletalMesh 掉落物也没有姿势复制或动画蓝图设置；选择类型应基于需要的视觉表现与物理资源。

### 4.2 冲击方向改成意图枚举（建议 4）

**问题**：这是本文档认为**第二重要**的一条。当前 `ELimbSpace` 把坐标系概念直接暴露给使用者，而 `BoneSpace` 的语义是"断口骨骼的朝向"，不是角色朝向：

```cpp
ELimbSpace::BoneSpace:  FinalImpactDirection = DismembermentWorldTransform.TransformVector(ImpactDirection);
```

同一个局部向量作用在左右肢体上，可能因局部轴不同而飞向不同方向，是否镜像相反取决于实际骨架。整网格模式下这里使用的是组件朝向。动作组要得到预期效果，需要知道目标局部轴；这适合用方向预设或可视化辅助解决。

**建议**：新增一层意图枚举，把局部空间转换收进引擎，让默认值就能给出"看起来对"的结果：

```cpp
/** 冲击方向预设：相对角色（或断口骨骼）的语义方向。 */
UENUM(BlueprintType)
enum class ELimbImpactDir : uint8
{
    None,
    Forward,        // 角色前方
    Backward,
    Right,
    Left,
    Up,
    Down,
    /** 沿被打断骨骼的延伸方向（手指/脚尖方向），最常用 */
    BoneAxis,
    /** 世界坐标，需要精确控制时才用 */
    CustomWorld,
    /** 完全自定义的局部向量，高级用法 */
    CustomBone
};
```

`FDismembermentConfig` 增加该字段，**默认 `BoneAxis` 或 `Right`**，让"什么都不填"也能出效果；`CustomWorld` / `CustomBone` 保留给需要精确控制的老用法，保证向后兼容。

配套把力度改为语义分级（动作组能秒懂），底层再映射到具体数值：

```cpp
UENUM(BlueprintType)
enum class ELimbImpactStrength : uint8
{
    Weak,       // 轻微脱落
    Medium,     // 默认
    Strong,     // 明显飞出
    Custom      // 使用 ImpactForce 原始值
};
```

**收益**：动作组不再需要接触 `ELimbSpace`、骨骼局部轴、向量归一化这些概念；同时因为默认值合理，可以做到"只填骨骼名就能跑通"。

### 4.3 关卡内即时预览（建议 5）

**问题**：现在验证一次改动的循环是：改参数 → 编译/保存 → Play → 走到能触发那帧动画的位置 → 看效果 → 退出。一次循环几十秒，调参数要循环几十次。这是**最消耗动作组时间**的地方。

**建议**：提供"不依赖动画也能触发"的调试入口，直接对视线内的角色触发指定骨骼的断肢：

```cpp
UFUNCTION(Exec)
void DismemberBone(const FString& BoneName);      // 控制台直接敲
```

再加一个**编辑器按钮**（`CallInEditor`），在选中角色后于细节面板一键触发，甚至不用进 PIE：

```cpp
UFUNCTION(CallInEditor, Category="Dismemberment|Debug")
void PreviewDismemberment();
```

注意 `CallInEditor` 在编辑器世界里的行为需要额外处理（必须用 `GetWorld()` 有效且允许 Spawn 的上下文），这部分要专门验证。如果实现成本高，只做控制台命令也能拿到大部分收益。

**顺带**：加一个"复原"入口，让预览后不用重开 PIE：

```cpp
/** 取消骨骼视觉隐藏；PBO_Term 终止的物理体需要另外恢复。整网格模式须重建组件。 */
UFUNCTION(BlueprintCallable, Category="Dismemberment|Debug")
void RestoreHiddenBones();
```

恢复提案还须记录已断状态和掉落物，并分别处理视觉隐藏、物理体重建、组件销毁。仅调用 `UnHideBoneByName` 不能称为完整恢复。

### 4.4 `bHideWholeTargetMesh` 语义收敛（建议 6）

**问题**：当前有两层布尔开关，另有目标限制——

1. `FDismembermentConfig` 里每条配置一个（`DismembermentComponent.h:32`）；
2. `UAnimNotify_ApplyDismemberment` 里一个通知级开关（`:28`），用 `|=` 合并进每条配置；
3. 还有一层隐含规则：整网格模式**必须**同时填 `TargetSkeletalMeshComponentName`，且**不能**指向主体网格（`DismembermentComponent.cpp:56-61`）。

对动作组来说，"隐藏整个网格"这个说法本身也不直观，而且"配置级 + 通知级"两个开关叠加的关系要靠读代码才能搞明白。

**建议**：显式建模成两种模式，做成一个下拉，而不是布尔：

```cpp
UENUM(BlueprintType)
enum class ELimbRemovalMode : uint8
{
    /** 隐藏一根骨骼及其子骨骼（单骨架角色的常规做法） */
    HideBone,
    /** 销毁一个独立的模块化网格组件（模块化身体的整块掉落） */
    DestroyWholeMeshComponent
};
```

- 通知级的那份配置**直接删掉**，统一到数据资产/每条配置一处，消除"哪个优先"的困惑。
- 选择 `DestroyWholeMeshComponent` 时，把 `TargetSkeletalMeshComponentName` 变成**必填**并在编辑器里标红；若填的是主体网格名，编辑器期就报错，而不是运行时静默 `return false`。

> 兼容性提醒：`bHideWholeTargetMesh` 是 `UPROPERTY`，改名会影响蓝图与已有资产（`DA_Dismemberment`、`BP_Dismemberment`、动画通知）。可以用 `UPROPERTY(meta=(DeprecatedProperty, DeprecationMessage="..."))` 过渡一个版本，或者接受一次性手工迁移并写进迁移说明。**这一条需要你先确认现有资产里用到该开关的地方有多少**（我读不到资产内容）。

### 4.5 组件参数按受众分层（建议 7）

**问题**：组件公开 6 个配置属性；避让时间和避让预设已位于 `Dismemberment|PhysicalSimulationAvoidance` 子分类，其余在 `Dismemberment`。仍可进一步把物理时长、LifeSpan 等参数放入进阶区域，让动作组集中处理常用配置。

**建议**：用 `meta = (AdvancedDisplay)` 或拆分 Category 做分层：

```
Dismemberment                    ← 动作组用
├─ Dismemberment Config Data
├─ Driven Skeletal Mesh Component Name   （建议自动探测，见下）

Dismemberment|Physics (Advanced) ← TA/程序用，默认折叠
├─ Physical Simulation Avoidance Time
├─ Physical Simulation Avoidance Collision Profile Name
├─ Limb Physics Simulation Time
└─ Detached Limb Life Span
```

**另外建议**：本机 UE 5.7 的 `ACharacter` 默认对象名就是 `CharacterMesh0`，不能将编辑器显示名 `Mesh` 当作必须修改默认值的依据。可以增加“留空时优先取 `ACharacter::GetMesh()`”的自动解析，并对多个候选明确报错。无论是否自动解析，整网格模式都应验证主体保护，而不能只依赖可能为空的驱动缓存。

### 4.6 把每条物理参数下沉到数据资产

延续 3.2 的思路，`LimbPhysicsSimulationTime` 与 `DetachedLimbLifeSpan` 目前是**组件级全局值**，但不同部位的合理值不同（手掌应该很快落地静止，整条手臂需要更久）。建议把这两个值同时放到数据资产层作为默认，并允许每条骨骼配置覆盖。

## 5. P2：打磨体验

### 5.1 断肢"定格在空中"（建议 8）

现有行为：避让时间与模拟时长之和到期后，只关物理模拟、不显式关闭碰撞。断肢可能悬停；是否阻挡角色取决于当前预设和通道响应。当前没有落地检测。

对动作组来说，这会造成两个可见问题：**空中悬停的断肢**和**挡路的隐形障碍**。

**建议**：提供可配置的收尾策略：

```cpp
UENUM(BlueprintType)
enum class ELimbSimulationEndBehavior : uint8
{
    Freeze,        // 现状：定格但仍碰撞
    FreezeNoCollision, // 定格并关闭碰撞（不再挡路）
    Sleep,         // 进入休眠（保留物理状态，性能更好）
    BoneAttach     // 吸附到地面
};
```

最省事的折中是至少让 `Freeze` 时**关闭碰撞或改为不阻挡 Pawn 的预设**。也可以考虑"停止模拟前先等它落地"——检测是否 `IsGrounded()`，落地即停，避免空中定格。

### 5.2 池化与性能（建议 9）

`ReInitializeLimb()` 已有部分复位（清两项物理计时器、复位网格状态、重建 `ActiveLimbComponent`），但组件每次仍新建 Actor，没有对象池调用方。真正池化还须补 LifeSpan、物理速度、脱离根节点后的重新挂接、组件变换、残留资源和归还策略。

如果动作组打算做"连续断肢""范围伤害断一片"这类效果，建议接上池化。同时注意：

- 默认 LifeSpan 为 30 秒，停止模拟延迟为 5.1 秒；名义上余下约 24.9 秒保留网格和碰撞配置，实际碰撞取决于预设。
- 高断肢量场景建议同时缩短 `LifeSpan`、启用 `FreezeNoCollision` 或 `Sleep`。

## 8. 可选：一个更彻底的方案

如果愿意投入更多，可以考虑把配置**从动画通知里彻底移出**，做成"部位 → 断肢表现"的注册表：

- 数据资产里，每个部位登记：候选模型、方向、力度、角冲量、物理时长、存活时间、碰撞预设（**全部在此配好**）。
- 动画通知里只留下**一个部位名下拉**（或一次多选）。
- 好处：动作组在动画上只做"选择"，所有表现参数由 TA 在一处统一把控，改一次全局生效，不会出现"十几个动画里参数各填一遍、还不一致"的维护灾难。

**权衡**：牺牲了"同一个部位在不同动画里表现不同"的灵活性。若确实需要，可以在通知里保留可选覆盖字段（留空即用注册表默认值）。

考虑到你们的资产命名（`右手` / `没手` / 配套死亡动画）看起来是**按角色/部位成套制作**的，我倾向认为这个"注册表"方案更贴合你的实际工作流——**但这一条要等你先回答第 7 节的问题 6 才能判断**。
