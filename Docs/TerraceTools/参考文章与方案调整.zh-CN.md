## 1. 最有价值的补充：先分级高度，再形成可编辑田块

现有 M1 解决“给定田块边界与标高，怎样落到真实 Landscape 上”。后续还需要解决“山坡上田块的边界与标高从哪里来”。第二篇的高度阶梯化适合作为后一问题的输入。

建议增加一个独立的自动规划入口：

```text
原始地形高度 + 制作范围
    → 高程分级 / 台地目标场
    → 提取区域边界、连通区域与邻接关系
    → 简化、拆分、删除窄田与小碎片
    → 生成可编辑 Terrace Plot
    → 地编调整、锁定或替换局部
    → 现有 Patch 整平后端
    → 田埂 / 挡土结构 / PCG 作物
```

作为概念示例，可先使用世界单位下的高度分级：

`Level = floor((Hsource - Hbase) / StepHeight)`

`Htarget = Hbase + Level * StepHeight`

这里是简化的分级示意，并非原文锐利/平滑函数的完整实现。阶梯转折可以再参数化，但应将“田面高度”“挡土连接”“田埂凸起”分开控制。直接生成一个阶梯高度场，还不会自动得到可耕作的有效田块。

该入口应使用固定世界高度基准和厘米单位，避免按每个块自己的最小/最大高度归一化，造成标高漂移或分块接缝。分析来源必须独立于当前工具已经修改过的合成地形，防止重复生成反馈自身结果。

## 2. 形状与种植的约束仍不可省略

自动规划需要处理同一高程的多个不连通区域、山脊/山谷分叉、区域孔洞、边界自交、最小田宽和田间通行。首版可拒绝孔洞，并将复杂区域拆成多个简单 Plot。层高与水平田宽受原坡度关联，不能承诺独立固定两者。

噪声或域扭曲可作为规划场、边界和局部风格的可选扰动，但水田标高必须保持平面；不向田面或水面逐点添加高度噪声。扰动后的边界仍需通过现有合法性检查。

实际农田还需要地编控制道路、进出水、排水和作物行向。这些属于本项目的场景生成规则，不应由高度函数隐式决定。

## 3. 可行走地形与预览显示分别设计

第二篇说明其预览网格未使用最终噪声高度作为实际顶点，显示阶段通过材质 Position Offset 和高度法线体现起伏。不能据此推导已具有与显示一致的行走碰撞。

本项目继续让 Patch 修改 Landscape 的真实高度，另行验证最终碰撞。自定义预览网格可以用于参数比较和工具反馈，但不能替代正式场景承载面；如以后使用网格承载，需要实际几何与相应碰撞数据。

窄田埂和挡土墙仍由网格补足。Landscape 的碰撞精度也需要检查，可用 Player Collision / Visibility Collision 视图对照最终几何；相关设置见 [Epic Landscape Collision Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-collision-guide-in-unreal-engine)。

## 4. 编辑器与资产设计

借鉴资产和工具分离的思路，后续增加可复用风格预设，存储田埂断面、材质、作物配置和默认生成参数；关卡中的目标 Landscape、成员归属及输出引用仍留在 Group。

在现有视口编辑和详情面板基础上，优先增加覆盖遮罩、目标标高、过渡带、冲突区域的调试显示。只有出现多个明确工作阶段、需要独立预览和大量参数时，再考虑专用工作流编辑器，不为初期小样先构建整套资产编辑器。

保存权威输入和必要生成数据。当前 M1 的持久化纹理方向可以保留；不以临时 Render Target 作为唯一数据来源，也不无条件序列化全部临时缓存。

## 5. 性能与示例迁移注意

若 CPU 遮罩或自动规划成为交互瓶颈，可将已校验的不可变快照交给后台任务计算，回主线程提交 UObject、纹理、事务和 Patch 变更。使用每组生成版本号、弱引用、取消/合并请求，防止旧任务覆盖新结果或访问已关闭工具。

原文为早期 UE5 示例；不直接移植 FRunnable 单例、原始编辑器指针捕获或底层 RHI 读写。若后续确需纹理 CPU/GPU 转换，应按本机 UE 5.8 API 验证资源生命周期、实际行跨度和同步成本。

## 6. 对开发顺序的影响

保留 M1 作为地形落地后端；先完成 M2 手绘田块的田埂、挡土结构和行走关系，再做 M3 作物分布，验证一小片完整可用梯田。

之后扩展自动规划入口，让它产出同一种 Plot 数据，复用已有后端与手工编辑流程。若未来美术明确将“一键铺整山”作为首要交付，再单独调整优先级。本文不将自动规划声明为已实现，也不直接放开 M1 对重叠过渡带和 World Partition 的限制。
